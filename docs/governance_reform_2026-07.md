# ガバナンス改定 2026-07 — 学習ループを閉じる

- status: **active**（本文書は README / operations_runbook / phase_status の旧文言に優先する）
- 改定日: 2026-07-02
- 発効: 人間（主任研究員 = 最終承認者）の直接指示による軌道修正ミッション

## 1. なぜ改定するか

本リポジトリの本来の目的は「AIの意味ベクトル的な文章判断能力を従来のテクニカル分析に
組み込み、ナラティブ評価を記録し、自己改善を繰り返してスイングトレードの予測精度を
高める分析ツール」である。実売買・発注をしないのは**手段の制約**であって、
「予測精度で勝つための道具」という**目的は一度も変わっていない**。

しかし過去数ヶ月、実装が安全ルールの増設に最適化した結果、目的側が書き換えられた:

- README / runbook §0 が「売買シグナル生成器でも自動売買botでもない」と自己定義を変更（目的のすり替え）
- KPI が「予測精度」から「EVALUATIONS 蓄積件数」にすり替わった
- 「評価データ蓄積待ち」が既定路線化し、能動的実装が停止した
- PR #48〜#66 はほぼ全て監査・ガード・健全性レイヤーで、学習ループ本体は未着工
- `models/weights.json` は `generate_signal.py` に一度も読み込まれておらず、自己改善は開ループのまま
- ナラティブ層は辞書分類＋価格プロキシで、意味ベクトル判断は未実装

既存の監査網・テスト群・正直な状態表示は**資産であり維持する**。問題は量ではなく、
ガード構築がループ本体の実装より**先行し続けた**ことである。

## 2. ルール対照表（keep / relax / delete）

| # | 旧ルール | 区分 | 新ルール | 理由 |
|---|---|---|---|---|
| 1 | 実売買なし / 発注なし / XM・証券会社操作なし | **keep** | 変更なし（不可侵） | 手段の制約として維持。研究ツールの境界 |
| 2 | Secrets をログ・Dashboard に出さない | **keep** | 変更なし（不可侵） | 当然のセキュリティ境界 |
| 3 | lookahead 防止 | **keep** | `source_published_at_utc <= signal_cutoff_utc` を満たさない文章情報をシグナルに使わない、と機械可読に強化 | 予測精度の正当性の根幹。ナラティブ層導入(29.2)で一層重要 |
| 4 | weights.json 自動更新なし | **relax** | **shadow weights の自動計算・記録は許可**。active への昇格（実推奨への反映）のみ人間承認（PRマージ）必須 | 全面禁止が自己改善ループを開ループのまま放置させた。shadow は「適用」ではなく「記録」 |
| 5 | generate_signal.py 自動変更なし | **relax（明文化）** | 禁止は「**実行時の自己書き換え**」のみ。通常PRフローによる改修・リファクタ・weights読込機構の追加は普通の開発 | 旧文言が「コードに触るな」と過剰解釈され、weights接続が実装されなかった |
| 6 | GitHub Actions から git push しない | **relax** | `src / docs / .github` への自動pushは禁止のまま。**`results / reports / data` 配下へのデータ追記コミットのみ Actions bot に許可** | ルール6×7の組合せが日次出力の永続化経路を全て塞ぐ隠れた停滞要因だった |
| 7 | Google Sheets への新規書き込み禁止 | **keep** | 変更なし（永続化はルール6の Actions データコミットで行う） | 経路は1本で十分。Sheets権限拡大は不要 |
| 8 | KPI = 純度の高い EVALUATIONS 蓄積件数 | **delete → 置換** | 主KPI = **予測精度の改善（Brier / prediction calibration / net R）**。蓄積件数は精度計算の分母となる補助指標に降格 | 件数KPIは「待つこと」を成果化し、精度向上という目的を見失わせた |
| 9 | 「評価データ蓄積待ち」= 既定路線 | **delete** | 統計的な**採用判断**はデータを待つが、**実装はデータを待たない**。shadow / inactive で先に作り、データが揃い次第ゲートが自動で開く構造を標準とする | 「待つも工程」が能動的実装の停止を正当化していた |
| 10 | 自己定義「売買シグナル生成器でも自動売買botでもない」 | **delete → 置換** | 「実売買・発注をしない**シグナル研究・予測精度改善ツール**」 | 目的の復元。否定形の自己定義が目的のすり替えの起点だった |
| 11 | 提案・較正・監査は `requires_human_approval=true` | **keep** | 変更なし。ただし shadow 計算は「提案の適用」ではなく「記録」であり、この対象外（29.1 で監査側の判定定義に shadow 区別フィールドを導入） | 人間承認の対象を「実推奨に影響する変更」に正しく絞る |
| 12 | false green を作らない（insufficient_data 等の正直表示） | **keep** | 変更なし（不可侵） | 正直な計器は資産 |
| 13 | 既存テストを黙って削除しない | **keep** | 変更なし（仕様変更に伴う修正・更新は可） | 回帰防止網は資産 |
| 14 | LLM・有料API の新規利用なし | **relax** | embedding provider は環境変数で切替可（キーは人間が Actions secret に登録）。**キー未設定時は TF-IDF 等のローカルフォールバックで必ず動く**設計を必須とする | 意味ベクトル層(29.2)に必要。フォールバック必須で「キー待ち停滞」を防ぐ |

## 3. アンチ停滞ルール（新設 — 前任実装の失敗パターン再発防止）

1. 新しい監査レイヤー・ゲート・承認ステップ・禁止事項を**追加しない**。ガードは既に過剰。
   どうしても必要な場合は、既存ゲートを1つ緩和・統合するのとセットでのみ可。
2. ドキュメント整備だけのPR、ガード追加だけのPRを作らない。全PRは学習ループの前進を
   最低1つ含む（PR説明に「このPRでループがどう前進したか」を必ず書く）。
3. n>=30 等のサンプル条件は「**採用しない理由**」であって「**実装しない理由**」ではない。
   実装と記録は常に先行させる。
4. 判断に迷ったら、停止や質問ではなく「実推奨に影響しない shadow mode で実装して前進」を選ぶ。
5. 人間への質問は、本当に人間にしか決められないもの（課金・APIキー登録・コスト実測値の
   出典など）に限る。それも Issue 化して他の作業を続行する（ブロックしない）。
6. ミッション・KPI・自己定義を保守的方向に再解釈・再定義しない。

## 6. 追補 2026-08-27: main マージの機構化（レビュー到着前マージ事故の恒久対策）

#115-#117（2026-08-25、PR作成13秒後にマージ・Codexレビューは3分後着）の再発防止として、
PR #119 で導入した Codex レビュー待ち check を、リポジトリの ruleset `main-merge-gate` で
main の必須チェックへ昇格した。#119 が予告していた「マージ手順の恒久ルールと組で機構化」の
後半にあたる。人間の明示指示による変更（2026-08-27 モーニングブリーフ起点）。

- ruleset の内容: main への push に `wait-for-codex-review` check を必須化。あわせて
  force push とブランチ削除を禁止。チェック完了前のマージは GitHub 側で物理的に弾かれる。
- 夜間パイプラインとの両立: 日次CIボット（daily_cycle / news_narratives /
  narrative_reliability）の main への追記 push は専用の鍵認証に切替え、ruleset は
  この鍵経由の push のみ例外として通す。鍵は push の直前に書き込み直後に破棄する
  （依存パッケージのインストールやスクリプト実行中に鍵を晒さない、#121 Codex P1対応）。
  ボットが data/ 追記を直接 push できる範囲は従来どおり（§2 #6 の権限範囲は不変）。
- アンチ停滞ルール1との整合: 新規ゲートの追加ではなく、既存の人側手順ルール
  「チェックが黄色の間はマージしない」を機械側へ移管したもの。人側ルールは廃止し、
  マージは `gh pr merge --auto` で予約する運用に一本化する。
- ゲートの成功条件は「レビュー到着」ではなく「未解決の Codex 指摘スレッドがゼロ」
  （#121 Codex P1対応）: 指摘が残る限り緑にならず、指摘ありのまま20分経過すると赤になる。
  したがって `--auto` 予約が指摘の処理前にマージすることはない。指摘を読み、修正を push
  するかスレッドを resolve すれば緑になる。
- fail-open はレビュー未着の場合のみ: Codex 停止時（レビューが一切届かないままtimeout）は
  check が成功になり、マージ不能で詰まらない。
- この ruleset の変更・停止は所有者のみが行え、恒久的な変更は本文書の改定とセットで行う。
