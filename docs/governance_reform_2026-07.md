# ガバナンス改定 2026-07 — 学習ループを閉じる

- status: **active**（本文書は README / operations_runbook / phase_status の旧文言に優先する）
- 改定日: 2026-07-02
- 発効: 人間（主任研究員 = 最終承認者）の直接指示による軌道修正ミッション

## 1. なぜ改定するか

本リポジトリの本来の目的は「AIの意味ベクトル的な文章判断能力を従来のテクニカル分析に
組み込み、ナラティブ評価を記録し、自己改善を繰り返してスイングトレードの予測精度を
高める分析ツール」である。実売買・発注をしないのは**手段の制約**であって、
「予測精度で勝つための道具」という**目的は一度も変わっていない**。

しかし過去数ヶ月、実装が安全ルールの増設に最適化した結果、目的側が書き換えられた:

- README / runbook §0 が「売買シグナル生成器でも自動売買botでもない」と自己定義を変更（目的のすり替え）
- KPI が「予測精度」から「EVALUATIONS 蓄積件数」にすり替わった
- 「評価データ蓄積待ち」が既定路線化し、能動的実装が停止した
- PR #48〜#66 はほぼ全て監査・ガード・健全性レイヤーで、学習ループ本体は未着工
- `models/weights.json` は `generate_signal.py` に一度も読み込まれておらず、自己改善は開ループのまま
- ナラティブ層は辞書分類＋価格プロキシで、意味ベクトル判断は未実装

既存の監査網・テスト群・正直な状態表示は**資産であり維持する**。問題は量ではなく、
ガード構築がループ本体の実装より**先行し続けた**ことである。

## 3. アンチ停滞ルール（新設 — 前任実装の失敗パターン再発防止）

1. 新しい監査レイヤー・ゲート・承認ステップ・禁止事項を**追加しない**。ガードは既に過剰。
   どうしても必要な場合は、既存ゲートを1つ緩和・統合するのとセットでのみ可。
2. ~~ドキュメント整備だけのPR、ガード追加だけのPRを作らない。全PRは学習ループの前進を
   最低1つ含む~~ → **2026-09-07 改定（下記 §3b）**。この条項が保守を止めていた実例が出たため。
3. n>=30 等のサンプル条件は「**採用しない理由**」であって「**実装しない理由**」ではない。
   実装と記録は常に先行させる。
4. 判断に迷ったら、停止や質問ではなく「実推奨に影響しない shadow mode で実装して前進」を選ぶ。
5. 人間への質問は、本当に人間にしか決められないもの（課金・APIキー登録・コスト実測値の
   出典など）に限る。それも Issue 化して他の作業を続行する（ブロックしない）。
6. ミッション・KPI・自己定義を保守的方向に再解釈・再定義しない。

## 3b. 変更の3区分（2026-09-07 改定 — アンチ停滞ルール2の置き換え）

### なぜ変えたか

旧ルール2「テストだけ・ガードだけ・ドキュメントだけのPRを作らない」が、**直すべきものを
直すのを禁止していた**。実例:

- 2026-09-06の監査T1で、TSOには **pytest を走らせる workflow が1本も無い**ことが判明した。
  さらに pytest が `requirements.txt` にすら無く、workflow を書いても
  `No module named pytest` で落ちる状態だった。結果、main に4件のテスト失敗が
  入ったまま誰にも見えていなかった。
- これを直すPRは「純粋な足回りの整備」で、予測精度は1ミリも上がらない。
  **旧ルール2が禁じている形そのもの**である。だから誰も出さなかった。

停滞を防ぐための条項が保守を止め、その結果テストが赤いまま気づかれない状態を作っていた。

### 新しい区分

**判定基準は差分の大きさではなく、その変更が何を動かすか。行数は見ない。**

| 区分 | 基準 | 手続き |
|---|---|---|
| **通常保守** | 提案・配分・採用判断に入る**数字の定義を動かさない** | 関連テスト＋通常レビュー。単独で完了してよい |
| **研究上の変更** | その**数字の定義を動かす** | 再現テスト＋変更前後の実測を PR に書く＋人間の判断 |
| **外部影響** | 実売買・発注・Secrets・外部サービスへの書き込み | 従来どおり（**緩和しない**） |

「小さいから通常保守」で通してはいけない。2026-09-06 の F1 の修正は数十行だが、
動かしたのは**提案の向き**（increase ↔ decrease）であり、研究上の変更である。
逆に、テストfixtureの修復やCIの整備は何行あっても通常保守で、**それだけで完了してよい**。

### 通常保守として単独で完了してよいもの（例示）

不具合修正 / 再現性の改善 / テストの修復・追加 / CI・足回りの整備 / 誤記の訂正 /
計器の可視化（緑の意味を区別できるようにする等）/ ドキュメントを実態に合わせる修正。

これらに「学習ループの前進」を抱き合わせることを求めない。必要な修正に不要な機能を
付ける圧力は、それ自体が停滞の原因である。

### 維持するもの（この改定で緩めていない）

実売買・発注の禁止 / Secrets保護 / 未来情報の混入防止 / 元データの保全 /
active な閾値・重みの変更は人間承認 / **Google Sheets への新規書き込み経路の追加禁止**
（§2 #7 の原文どおり。既存の承認済み同期——`daily_cycle.yml` と
`reevaluate_pending.yml` の Sheets 書き込み——は grandfather する。
「Sheets書き込み禁止」と縮めて書くと正規の日次同期まで止める規約になる。#156 Codex P2）/
false green を作らない / 既存テストを黙って削除しない。

### 過去フェーズの設計固定について

`phase29_design_reasoning.md` の「再設計しない」「統計手法は既存のものだけ」
「チェックリストをそのまま実行」は、**当該フェーズ限定**と読む。再現可能な欠陥が
示されたときは変更提案してよい。ただし「都合のよい結果を得るための閾値変更」とは
区別する——**欠陥の再現手順が先にあること**が条件。

## 6. 追補 2026-08-27: main マージの機構化（レビュー到着前マージ事故の恒久対策）

#115-#117（2026-08-25、PR作成13秒後にマージ・Codexレビューは3分後着）の再発防止として、
PR #119 で導入した Codex レビュー待ち check を、リポジトリの ruleset `main-merge-gate` で
main の必須チェックへ昇格した。#119 が予告していた「マージ手順の恒久ルールと組で機構化」の
後半にあたる。人間の明示指示による変更（2026-08-27 モーニングブリーフ起点）。

- ruleset の内容: main への push に `wait-for-codex-review` check を必須化。あわせて
  force push とブランチ削除を禁止。チェック完了前のマージは GitHub 側で物理的に弾かれる。
- 夜間パイプラインとの両立: 日次CIボット（daily_cycle / news_narratives /
  narrative_reliability）の main への追記 push は専用の鍵認証に切替え、ruleset は
  この鍵経由の push のみ例外として通す。鍵は push の直前に書き込み直後に破棄する
  （依存パッケージのインストールやスクリプト実行中に鍵を晒さない、#121 Codex P1対応）。
  ボットが data/ 追記を直接 push できる範囲は従来どおり（§2 #6 の権限範囲は不変）。
- アンチ停滞ルール1との整合: 新規ゲートの追加ではなく、既存の人側手順ルール
  「チェックが黄色の間はマージしない」を機械側へ移管したもの。人側ルールは廃止し、
  マージは `gh pr merge --auto` で予約する運用に一本化する。

**2026-09-06 追記（監査T1）**: 必須チェックに `pytest` を追加した。それまで TSO には
pytest を走らせる workflow が **1本も無く**（`pull_request` で走るのは `pr_review_gate.yml`
のみ）、しかも `pytest` が `requirements.txt` に入っていないため、workflow を書いても
`No module named pytest` で落ちる状態だった。結果、main に4件のテスト失敗が入ったまま
誰にも見えなかった。`.github/workflows/tests.yml` を新設して `pytest` を必須チェックへ
昇格（DeployKey のバイパスは不変なので夜間ボットの push は従来どおり通る）。

これは「Actions が success ならテストが通っている」という読み替えの事故であり、
ERS で踏んだ「workflow が success なら観測している」（5営業日消えた）と同型。
**緑の意味を確かめずに緑を信じない。**
- ゲートの成功条件は「レビュー到着」ではなく「未解決の Codex 指摘スレッドがゼロ」
  （#121 Codex P1対応）: 指摘が残る限り緑にならず、指摘ありのまま20分経過すると赤になる。
  したがって `--auto` 予約が指摘の処理前にマージすることはない。指摘を読み、修正を push
  するかスレッドを resolve すれば緑になる。
- fail-open はレビュー未着の場合のみ: Codex 停止時（レビューが一切届かないままtimeout）は
  check が成功になり、マージ不能で詰まらない。
- **2026-11-24 の改定: 「指摘なし」のレビューを「未着」と数えていた。** Codex は指摘が無いときレビューを作らず、
  要約コメントを completed・指摘なしに書き換えて 👍 を付けるだけで、reviews API には何も出ない。ゲートは
  reviews API しか見ていなかったので、Codex が2分で読み終えた PR を20分待ち、「レビュー未着のまま通過
  (fail-open)」と PR に書いていた。黄色い通知が「未レビュー」と「レビュー済み」の両方に付いていたので、
  通知を見ても区別できなかった（9/6 に「同じ緑が2つの意味を持つ」を直したときと同じ形）。
  通知を入れた 2026-09-06 から 11-24 までにマージされた 73本（#152〜#229）を数えた結果:

  | 黄色い通知 | 本数 | 中身 |
  |---|---|---|
  | 付いた | 68 | |
  | └ 実際はレビュー済み・指摘なし | 33 | #184〜#228 のうち。要約の状態が、マージした head を completed・指摘なしと言っている |
  | └ 本当に最後のコミットが未レビュー | 10 | 8本は、指摘を直して push したあとの head を誰も読んでいない（#188・#189・#200・#201・#202・#204・#206・#210）。2本は Codex のレビューが終わらなかった（#190・#191） |
  | └ 判別できない | 25 | #152〜#183。要約コメントが古い書式で、機械可読な状態を持たない |

  （PR #229 と最初の版のこの節は「11/15〜11/23 の12本」と書いたが、数え間違い。#217〜#228 でマージ済みなのは 11本で、
  誤表示はそれよりずっと前から続いていた。）
  - いまは、要約コメントの機械可読な状態（`codex-review-state:v1`）が**いまの head** を completed・指摘なしと
    言っていれば、レビュー到着として扱う。未解決スレッドがゼロならその場で通す（20分待たない。黄色い通知も書かない）。
  - 要約が「いまの head に指摘あり」と言うのに、レビュー（指摘スレッド）が見えないまま timeout したら赤にする。
    指摘があると分かっている PR を fail-open で通さない（#162 で起きた形）。
  - 通知が付くのは、いまの head について、レビューも、completed の要約も、最後まで現れなかったときだけ。

    依頼は Codex に接続した人のアカウントからでないと通らない。ERS のゲート（ERS-ADR-0082、2026-09-07）は同じ方式を
    入れているが、ERS の PR #82 でも Codex は8回とも同じ返事をしており、入れた日から働いていない
    （初版は「4回」と書いたが、一覧が途中で切れていた数字。2026-11-25 に全件を数え直した）。
    通すには、人のアカウントの鍵を GitHub の Secrets に置いてゲートに使わせる必要がある（鍵を作るのは所有者。未実施）。
  - 2026-11-24 の2つ目の改定（PR #230）: 時間切れで通すときの通知を、理由ごとに分けた。**fail-open の方針は変えていない。**

    |---|---|---|
    | 🟠 push されたあとの head を、誰もレビューに出していません | push された head で、その push より後に人の依頼が無く、Codex が読み始めた跡も無い | レビュー依頼のコメントを書く |

    | 🔴 レビュー枠切れ | Codex が利用上限に達している | 枠の回復を待つ |

    依頼の有無を読めなかったとき（GitHub からの取得の失敗）は、🟠 にしない。「誰も頼んでいない」と言い切れないため。
  - 同じ PR の古い実行は畳む（`concurrency`）。続けて push すると古い実行が古い head を待ち続け、20分後に古い head について
    通知を書いていた。
  - **残っている穴: 修正を push したあと誰も依頼しなければ、その head は 🟠 の通知つきで、未レビューのまま通る。**
    通知は正確になったが、止めはしない。止める（赤にする）か、鍵を置いてゲートに頼ませるかは、所有者の判断。
  - **2026-11-25 の改定: Codex が同じ head を読み直している最中は、前の回のレビューで先に通さない。**
    同じ head に前の回のレビュー（指摘は解決済み）が残っていると、読み直しを頼んだ直後でも「レビュー到着・未解決ゼロ」で
    その場で通っていた。`--auto` の予約があればそこでマージされ、読み直しの結果はマージの後に届く（このゲートが防ぐために
    在る事故と同じ形）。ERS の同型のゲートを直したとき（ERS の PR 92）に Codex が指摘した穴で、こちらにも残っていた。
    - 要約が「いまの head を読んでいる最中」と言うあいだは通さない。要約を読めなかった周回では、最後に読めた内容に従う。
    - そのあいだも未解決スレッドは数えて覚えておく。時間切れのとき、最後に数えた結果が未解決（または数えられなかった）
      なら赤。未解決ゼロのまま読み直しが終わらなければ、上の表の 🟡（読み始めたが終わらなかった）で通す。
    - 手順は変わらない。指摘を承知で通すときは、スレッドに理由を返信して resolve する。**そのあと同じ head の読み直しを
      頼んだら、結果が出るまでゲートは待つ**（頼まなければ、これまでどおり、resolve した時点で通る）。
    - 入れていないもの: 要約が先に「指摘あり」へ変わり、新しい指摘スレッドが遅れて見える順番への備え。ERS の PR 92 で
      見た3回は、どれも結果（レビュー）が先で、要約の書き換えが2〜3秒あとだった。その順番ならこの改定で足りる。
      逆の順番が実際に起きたら、ERS のゲートが入れた確かめ方（その head への Codex の行コメントが増えたことを見る）を移す。
  - **判定は `pr_review_gate.yml` の中だけにある。** 2026-09 に書いた別の判定器（`tools/codex_review_state.py`）と
    承認スクリプト（`tools/resolve_gate_ack.sh`）は、ゲートにつなぐ PR が出ないまま main に残っていた（#163 を閉じたあと、
    中身だけが #165 の squash に巻き込まれて入った）。どこからも呼ばれず、Codex の古い書式（要約の表）を読む作りだったので、
    2026-11-24 に外した。「指摘を承知のうえで通す」ための `GATE-ACK` コメントも、この判定器の中にしか無かった。
    **`GATE-ACK` と書いても何も起きない。** 指摘を承知で通すときは、指摘のスレッドに理由を返信して resolve する（記録が PR に残る）。
  - **PR の説明文やコメントに、例示として `@codex …` と書かない。** Codex は文中の言及も呼び出しとして読む。
    2026-11-24 の PR #230 は、説明文に依頼の文言を例として書いたところ、Codex が「この repo の環境を作れ」と返信し、
    PR を開いたときの自動レビューが始まらなかった（バッククォートで囲んでも読まれた）。文書・コード・コミットメッセージは
    読まれない。説明文やコメントでは「レビュー依頼のコメント」のように言い換える。
  - 判定は `src/test_pr_review_gate_workflow.py` が、workflow の手順をそのまま走らせて確かめる。
- この ruleset の変更・停止は所有者のみが行え、恒久的な変更は本文書の改定とセットで行う。
