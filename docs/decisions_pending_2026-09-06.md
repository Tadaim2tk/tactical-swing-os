## 決定1: 「5営業日」は5本目か6本目か（監査F5）

### 事実

同じ「5日」という言葉が、2箇所で1バー違う量を指している。

| | 定義 | 実装 |
|---|---|---|
| 採点 `r_close_5d` | 判断後の**5本目**の終値 | `j = k - 1 + h`（h=5 → `k+4`） |
| 執行の時間決済 | 判断日起点+5 = **6本目**の終値 | `deadline = idx0 + EXIT_DEADLINE_BARS`（=5） |

監査の合成データでは、5本目は7/7終値104、執行は7/8終値105で決済。
fill 101 / risk 6 なら **+0.5000R と +0.6667R** の違いになる。

さらに: 暗号資産の5バー（5暦日）と週5日市場の5バー（7〜10暦日）は同じ暦日長ではない。
「5日」という語は**3つの別々の量**を指しうる。

### 選択肢

1. **執行を5本目に合わせる**（`EXIT_DEADLINE_BARS` を実質4へ）。採点と一致するが、
   現在の執行テストは6本目を期待しており、trackedシムの時間決済44件の結果が動く。
   「5営業日保有」という運用上の直感とはズレる（判断日を1日目と数えるなら5本目は4日後）。
2. **採点を6本目に合わせる**。全702行の再採点が必要。過去の較正数値（月次の (a)(b)(c)）が
   すべて動く。
3. **両方を残し、名前を分ける**。`r_close_5bars`（採点）と `exit_at_bar6`（執行）のように
   別の名前にして、同じ「5日」で呼ぶのをやめる。数値は動かない。

### 私の推奨

**3 → その後で1か2**。まず名前を分けて「同名の別物」を解消し、どちらへ寄せるかは
その後に別途決める。理由は、いま数値を動かすと F1/F6 の修正で動いた数値と混ざり、
どの変化が何由来か分からなくなるため。監査自身も「定数を勝手に1引く修正ではなく、
どちらを意図したかの契約統一が必要」と書いている。

### 決めないと何が困るか

週次・月次の R がどちらの定義か曖昧なまま積み上がる。特に「5日時間決済は TP1決済より良い」
（仮説登録簿の「生存」1件、+0.084%/注文）は執行側の6本目で測られており、
採点側の5本目とは別の量を根拠にしている。

## 決定2: 数値の契約を固定する（監査D1）

### 事実

方向あり193行の実測:

- 記帳RRと `entry中点/SL/TP1` 再計算の差が0.10超: **83行**。RR>=1.5 判定が違う: **60行**
- `expected_r` と `p*RR-(1-p)` の差が0.10超: **123行**

後者は「123行の誤計算」を意味しない。GPTには主観値の記入を許しており、式・予測事象・
時間決済の扱いを固定していないためである。**同名・同じR表記で区別できない**のが問題。

例: 9/4 WTI は RR=2.89、p=.57、申告 expected_r=.39。二点分布式なら 1.2173R。
時間決済の連続損益を予測しているなら両立し得るが、その分布・定義は記録されていない。

### 固定すべき項目（監査の表をそのまま採る）

| 項目 | 固定すべき意味 |
|---|---|
| `win_prob` | 何が起きる確率か、何バーまでか、約定条件付きか |
| `expected_r` | 主観期待か二点分布計算か、利確/時間決済/未約定/コストの扱い |
| realized R | midpoint基準の方向Rか、fill基準の執行Rか、gross/netか |
| `sample_count` | 全記録数、評価可能数、確定数、独立な機会数のどれか |
| `impact` | 平均差/合計差/勝率差の区別、前後n、単位、同じhorizonか |
| `capital_pct` | 単純なR×固定元本リスク合算か、複利口座損益か、同時保有の扱い |
| `as_of` | 判断時刻・データ確定時刻・採点時刻と評価窓の起終点 |

### すでに部分的に手を付けたもの

- `sample_count`: PR #145 で「測れた行数」に固定し、`recorded_count` / `unevaluable_count` を分離
- horizon: PR #150 で `r_horizon` 列を追加（どのhorizonのRを採ったか）
- `scale_check`: PR #147 で `passed`/`excluded`/`not_checked` を明示

残りは `win_prob` / `expected_r` / realized R / `impact` / `capital_pct` / `as_of`。

### 私の推奨

**`expected_r` から着手する。** ここだけが「GPTの主観」と「機械の計算」が同じ列名で
混在しており、しかも A級判定（`expected_r>=0.45`）に直結している。

具体案: 台帳に `expected_r_basis` 列を足し、`subjective` / `two_point` のどちらかを
GPTに明示させる。列を足すだけなので LOG28列の契約は壊れない（サイドカー方式）。

**ただしこれは日次プロンプトの改定を伴うので、あなたの承認が要る。**
changelog(12)(13)(14) と同じ扱いになる。

### 決めないと何が困るか

`impact` の混同（F4）を直そうにも、比較すべき「同じ量」が定義されていない。
F4 は P2 として残っているが、D1 が決まらないと直しようがない。

## 決定3: ガバナンス規約の3区分化

### 事実

批評とCodexの両方が同じ結論に達している。特にCodexが指摘した接続:

> 「テストだけのPR禁止」「ガードだけのPR禁止」「全PRで学習ループを前進」。
> **T1はまさにこの規約が禁じている形のPRです。** 純粋なテストfixture修復。
> だから4件の失敗がmainに残りました。

私の実測でも、T1は結局「fixture修復」ではなく「CIにpytestを入れる」だったが、
どちらにせよ現行規約なら「学習ループを前進させていない」PRである。

### 提案されている区分

Codexの切り口を採る。**差分の大きさではなく、その変更が何を動かせるかで切る**:

| 区分 | 判定基準 | 手続き |
|---|---|---|
| 通常保守 | 提案・配分・採用判断に入る数字の**定義を動かさない** | 関連テスト＋通常レビュー |
| 研究上の変更 | その数字の定義を**動かす** | 独立研究レビュー＋人間判断 |
| 外部影響 | 実売買・発注・Secrets・外部への書き込み | 従来どおり（緩和しない） |

**行数は見ない。** F1の修正はおそらく数行だが、動かすのは提案の向きである。
「小さいから通常保守」で通すと、一番危ないものが一番軽い経路を通る。

### 維持するもの（緩和しない）

実売買・発注の禁止 / Secrets保護 / 未来情報混入防止 / 元データ保全 /
active変更の承認 / Sheets書き込み禁止。

### 私の推奨

**この決定だけは、私が自分で決めるべきではない。**

規約を緩める提案を、その規約に縛られている側が起案して自分で承認するのは筋が悪い。
内容には賛成だが、承認はあなたがしてください。

なお **「規約を外せば是正が進む」わけではない**、という批評自身の釘を支持する。
今回のF1〜F9は規約の重さの問題ではなく測り方の問題であり、規約を緩めても
数字が意味を持つようにはならない。ただし逆向きの因果（規約が是正作業を抑えていた）は
実在すると思う。phase29の「統計手法は既存のものだけ」「再設計しない」は、
F1の指標定義を直す作業を正面から禁じている。

### 決めないと何が困るか

D1の契約固定は、性質上「ガードだけのPR」になる。現行規約のままだと着手しづらい。
